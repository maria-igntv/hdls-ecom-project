# Проверка этапа 2

Проверка выполнена командой `python3 scripts/check_stage2.py` на реальном PostgreSQL/Redis и двух Spring Boot API за HAProxy. Применены Flyway-миграции. Тест использует отдельный Compose-проект со случайным именем; после завершения его контейнеры и временный volume удалены.

## Окружение и границы

Java 25, Spring Boot 3.5.16, PostgreSQL 17, Redis 7.4, HAProxy 3.2; Docker Engine 29.9.2, aarch64, 12 виртуальных CPU и около 7,75 ГиБ доступной Docker RAM. Контейнеры ограничены конфигурацией [Compose](../infra/stage2/compose.yaml). Данные и Basic-учётные записи синтетические. Клиентский пул — 64 параллельных потоков; 1000 запросов не означают 1000 одновременно исполняемых SQL-транзакций.

Это проверка бизнес-корректности и восстановления. Общий API-пик модели около 640 RPS, p95/p99 и целевое production-оборудование данным прогоном не сертифицируются. Стресс-таймауты длиннее предварительных latency SLO.

## Проверки

| Сценарий | Полученный результат |
| --- | --- |
| 1000 попыток на запас 100 | 100 заказов, 900 OUT_OF_STOCK, reserved = 100 |
| Продолжительность этого окна | 4.23 с; это один прогон, не профиль устойчивой нагрузки |
| Повтор с прежним ключом | Тот же созданный заказ и ответ; другой запрос с тем же ключом отклонён |
| После удаления краткоживущего idempotency response | Заказ найден по долговременному уникальному ключу, новый резерв не создан |
| 64 конкурентных одинаковых запроса | 1 заказ, 1 резерв |
| Несколько SKU, один отсутствует | Ни одного частичного резерва; после restock прежний отказ воспроизведён, новый ключ создал заказ |
| Обратный порядок добавления SKU | Два заказа успешно обработаны, deadlock не возник |
| Цена изменилась | Кэш обновлён между API; checkout со старой суммой отклонён; снимки старого заказа не изменились |
| Попытка уменьшить on_hand ниже reserved | Отклонена |
| Single-flight | 64 обращений к холодному SKU на одном API → 1 origin-load |
| Redis остановлен | Карточка и checkout продолжили работать через PostgreSQL |
| Два одновременных запуска expiry | Резерв освобождён один раз; повторный запуск ничего не освободил |
| Владелец/роль | Без входа 401, покупателю запрещён admin API, чужой заказ возвращает 404 |
| Совпадение агрегата запасов | Для всех SKU reserved совпал с суммой ACTIVE reservation_items; отрицательных/избыточных остатков нет |

WAL за окно 1000 попыток: 1109608 байт. Это конкретная смесь из 100 созданий, 900 отказов и индексов/событий на синтетической схеме; нельзя использовать её как универсальную стоимость одного заказа или всей записи сервиса.

## SQL-планы

Перед анализом добавлены 200 тыс. исторических заказов и 600 тыс. позиций; старые резервы не требуются после их 30-дневного retention. В outbox добавлена опубликованная история, чтобы проверить частичный индекс непубликованных событий. Выполнен ANALYZE.

| Запрос | Выбранные индексы | Execution Time, мс |
| --- | --- | --- |
| card | products_pkey, product_prices_pkey, inventory_pkey | 0.743 |
| category | products_pkey, product_prices_pkey, inventory_pkey | 1.496 |
| history | orders_user_cursor | 0.142 |
| expiry | orders_expiry | 0.461 |
| outbox | outbox_unpublished | 0.449 |

Полные [JSON-планы](stage2_query_plans.json) содержат actual rows и BUFFERS. Для категории выбран PK scan; MATERIALIZED CTE ограничивает число JOIN размером страницы. Составной индекс не объявляется использованным, если этого нет в плане. Времена относятся к этому объёму/окружению и состоянию кэшей.

## Восстановление

`pg_dump -Fc --no-owner --no-acl` создал dump размером 29968427 байт за 1.62 с. `pg_restore --single-transaction --exit-on-error` восстановил его в новую БД за 4.69 с.

Восстановлено 200106 заказов и 600109 позиций. Совпали отсортированные контрольные отпечатки заказов/остатков, количества позиций, резервов, outbox и idempotency. Исходная БД не перезаписывалась.

Проверен логический dump/restore PostgreSQL. PITR, автоматический failover, потеря AZ, backup медиа и гонка с реальным платежом не входили в этот прогон. Эти границы сохраняются при формулировке SLO следующих этапов.
