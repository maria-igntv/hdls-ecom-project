# Проверка этапа 4

Этап добавляет оплату через устойчивый локальный Java-эмулятор, доставку outbox через RabbitMQ, отдельный Search API/OpenSearch и изображения Garage S3 с Nginx cache. Архитектурные решения, таймауты, последовательности и runbook DLQ описаны в [interactions.md](interactions.md); внешний контракт — [OpenAPI](openapi.json).

## Локальный запуск

Нужны Docker Desktop с Linux ARM64/AMD64-контейнерами, Docker Compose и Python 3. Сборка использует Maven/Java 25 внутри контейнеров. Проверочная машина: Mac M4 Pro, Docker Engine с 12 CPU и примерно 7,75 ГиБ RAM. Первоначальная сборка/скачивание образов требует интернета. Существующая ВМ без интернета в этом этапе не используется.

Из корня репозитория, после остановки других учебных стендов, занимающих 18080–18087:

```bash
docker compose -f infra/stage4/compose.yaml up -d --build
python3 scripts/init_stage4.py
curl http://localhost:18080/readyz
curl 'http://localhost:18080/api/search?inStock=true&limit=5'
```

Readiness Commerce становится 200 после SQL и startup-прогрева. Поиск проходит readiness после первоначального rebuild каталога; HAProxy проверяет его раз в 2 секунды с rise=2. До завершения поиска категории и карточки работают независимо. Garage init можно повторять: layout RF=1, бакет product-images, фиксированный тестовый ключ и публичный read-only website endpoint.

| Loopback-порт | Назначение |
| --- | --- |
| 18080 | HAProxy: Commerce и `/api/search` |
| 18081/18082 | Прямые Commerce API |
| 18084 | Runtime socket HAProxy |
| 18085 | Прямой Search API |
| 18086 | Публичные изображения через Nginx cache |
| 18087 | Эмулятор провайдера, Bearer local-provider-token |
| 19200 | OpenSearch REST, локальная отладка |
| 15672 | RabbitMQ management: commerce / local-rabbit-password |
| 13900 | S3 API Garage с SigV4 |

Все пароли/ключи в Compose — открытые учебные фикстуры. Внешний эквайринг, SMTP, внешний CDN, TLS и многозонное размещение здесь не подключены. Provider владеет отдельной SQL-схемой provider; её таблицы не связаны FK с Commerce. На одном стенде используется общий PostgreSQL-процесс и тестовая DB-учётная запись; это экономия локальных ресурсов, а не изоляция отказов провайдера в целевой системе.

### Демонстрация оплаты

Создать заказ по [инструкции ядра](backend_api.md), затем подставить фактический orderId:

```bash
curl -u buyer-1:demo-buyer-1 -X POST \
  http://localhost:18080/api/orders/ORDER_ID/payments
```

Полученный paymentId используется для имитации оплаты:

```bash
curl -X POST -H 'Authorization: Bearer local-provider-token' \
  -H 'Content-Type: application/json' -d '{"state":"SUCCEEDED"}' \
  http://localhost:18087/demo/payments/PAYMENT_ID/state

curl -u buyer-1:demo-buyer-1 http://localhost:18080/api/orders/ORDER_ID
curl -u buyer-1:demo-buyer-1 http://localhost:18080/api/orders/ORDER_ID/payments
```

Эмулятор сохраняет состояние до ответа и доставляет подписанный callback из собственной SQL-таблицы. Повтор SUCCEEDED не создаёт второе списание. Эмулятор можно перезапустить без потери платежей/недоставленных callbacks. Для демонстрации отказа используется state=FAILED. Неоплаченная сессия провайдера автоматически закрывается в FAILED после 30 минут; локальная сверка затем прекращает её опрашивать. Для таймаута доступен PUT /demo/faults с createDelayMs до 10000 и pauseCallbacks; он защищён тем же Bearer-токеном и предназначен только для этого локального эмулятора.

### Изображения и перестроение поиска

```bash
curl -u admin:demo-admin -F 'file=@/absolute/path/image.png;type=image/png' \
  http://localhost:18080/api/admin/products/1/images

curl -u admin:demo-admin -X POST http://localhost:18080/api/admin/search/rebuilds
curl -u admin:demo-admin http://localhost:18080/api/admin/search/rebuilds
curl -u admin:demo-admin http://localhost:18080/api/admin/background-stats
```

URL изображения возвращается загрузкой и появляется в карточке после invalidation. При поиске изменение становится видимым асинхронно. Rebuild сохраняет старый LIVE index до успешного переключения alias, а незавершённый scan продолжается с сохранённого cursor.

## Автоматические проверки

```bash
python3 scripts/check_stage4.py
```

Команда создаёт собственный проект со случайным суффиксом, применяет миграции/fixtures и инициализирует Garage. Выполняет HTTP/SQL/AMQP/S3-проверки, сохраняет подробности в artifacts/stage4 и успешную сводку в [stage4_checks.json](stage4_checks.json), затем удаляет только собственные контейнеры/volumes. Нужны свободные loopback-порты. `--keep` сохраняет тестовый стенд; STAGE4_PROJECT задаёт явное имя. `--existing` предназначен для диагностики незавершённого прогона на этом же проекте, не для повторного измерения на произвольных пользовательских данных.

Проверяются:

- Первоначальный индекс из 100 тыс. товаров; русский анализатор и фильтры.
- 32 параллельные инициации одного платежа → одна локальная/внешняя запись; чужой заказ закрыт 404.
- HMAC и десять повторов одного webhook → одно изменение запаса.
- Провайдер фиксирует создание и задерживает ответ на 5 с; Commerce timeout 3 с оставляет PENDING. При отключённых callbacks worker восстанавливает PAID сверкой.
- Автоматическое истечение, закрытие брошенной сессии провайдера после 30 минут, FAILED до expiry, поздний SUCCEEDED → REFUNDED без уменьшения доступного запаса.
- 24 гонки оплаты и expiry → только PAID/SUCCEEDED либо EXPIRED/REFUNDED; равенство зарезервированного количества ACTIVE-позициям.
- Остановка RabbitMQ → checkout работает, outbox сохраняется и догоняет после восстановления.
- Остановка OpenSearch → Search 503, checkout работает; после ограниченных попыток задание попадает в DLQ и успешно возвращается после исправления зависимости.
- Падение publisher после confirm до published_at → повтор после lease без потери события.
- Падение consumer после внешнего уведомления до inbox/ack → одно уведомление благодаря eventId на стороне sink.
- Rebuild с изменением уже просканированного товара, устаревшая external version и скрытие товара.
- Загрузка изображения в Garage, GET/HEAD через медиаконтур, запрет записи через Nginx, URL в карточке, очистка объекта после моделируемого падения до SQL-финализации.
- Неизвестная schema_version → карантин DLQ после ограниченных повторов.

Для аварийных границ используется таблица demo_faults, доступная напрямую только проверочному коду. В активном demo-profile одноразовый переключатель вызывает Runtime.halt(91). Обычный запуск не содержит переключателей, HTTP-метода для их включения нет. RestartCount Docker сбрасывается при ручном старте контейнера, поэтому тест отдельно проверяет аварийный перезапуск и конечный бизнес-эффект.

JUnit Jupiter/AssertJ/Mockito выполняются `mvn verify` в Docker build. К 17 проверкам readiness/validation добавлены 10 вариантов переходов платежа, проверка raw-body HMAC и отказ от ложного image/png. Конкурентные транзакции проверяются на реальном PostgreSQL, а не Mockito. Исходные миграции V1/V2 сохранены; V3 вводит платежные leases/inbox, queue/rebuild/media state, V4 — ротацию cleanup.

## Нагрузка

После запуска полного стенда:

```bash
python3 scripts/load_stage4.py --project hdls-stage4 --seconds 300 --cold-cache
```

Генератор выполняет 60 с прогрева и 300 с измерения на ~640 основных API RPS, отдельно 161 media GET/с. Опция --cold-cache предварительно очищает только Redis выбранного учебного проекта: прогрев начинается с пустым кэшем. Количество origin-loads ограничено четырьмя на API, ожидание слота в полном стенде 500 мс; минимальные конфигурации прежних этапов сохраняют 100 мс. Вес операций берётся из model/capacity.json, добавлены поиск, инициирование платежа, webhook и загрузки. Перед тестом добавляется история 200 тыс. заказов/600 тыс. строк и 100 тыс. уже опубликованных outbox fixtures, если её ещё нет. Объект media — корректный PNG размером около 120 КБ; он проходит настоящий PUT в Garage. Для редкой операции загрузки используется маленький PNG. Это разные сценарии расхода памяти/сети.

Подготовка корзин/заказов/платежей и имитация действий провайдера учитываются как support traffic сверх основных 640 RPS. Эмулятор также отправляет собственные callbacks; это дополнительный фоновый трафик. Из-за независимых arrival-сценариев округление даёт небольшое отличие configuredRate от 640. Checkout, payment и webhook используют разные группы покупателей, чтобы тест производительности не превратился в гонку одной корзины. Конкурентные бизнес-конфликты проверяются отдельно.

Пороговые цели: технические/неожиданные/support ошибки <0,1%, dropped=0, общий API p95<200/p99<500 мс, checkout/payment/webhook p95<500 мс, поиск p95<300 мс, media p95<200 мс. Контролируются CPU/working set контейнеров, RSS Java, deadlocks, outbox drain и бизнес-инварианты. В Git хранится [сводка](stage4_load_results.json); подробные k6/resources — в artifacts/stage4/load. Результат короткого смешанного прогона не заменяет часовой soak этапа 3 на новом составе системы.

## Полученные результаты

В [интеграционной сводке](stage4_checks.json) все сценарии завершились успешно. В 24 гонках получены 14 PAID/SUCCEEDED и 10 EXPIRED/REFUNDED; нарушений инвариантов 0. Отдельное обновление стало видимым в поиске за 1,023 с. На постоянном стенде финальной сборки дополнительно проверены сохранение trace_id при сверке и формат двух реально опубликованных envelope. Это один опыт freshness, а не доказательство месячного SLO 99% ≤10 с.

Все пороги основного профиля пройдены. Публикации догнали outbox; pending/refund_pending не накопились. Измерение API выполнялось внутри Docker-сети, без TLS и пользовательского WAN. Media p95 относится к локальному cache hit. Синтетические карточки компактнее аппаратной модели; поиск выполнялся с совпадающим запросом product, категориями и фильтром наличия.

Финальный прогрев начался после очистки Redis: 38 413 основных запросов за 60 с, технических/неожиданных/support ошибок 0, dropped 0, все пороги пройдены. API p95 2,758 мс, p99 133,776 мс. В полном стенде ожидание origin-slot увеличено со 100 до 500 мс, число одновременных загрузок остаётся 4 на API. При настоящем насыщении остаётся ограниченный отказ CATALOG_BUSY; безлимитный fallback к БД не вводился. Это опыт с пустым Redis после readiness, а не холодный старт всей инфраструктуры. Часовой soak нового полного состава остаётся отдельной проверкой.

Предыдущие измерения сохранены для прозрачности. [Первый прогон](stage4_initial_load_results.json) прошёл основной профиль, но на прогреве редкие imageUpload/stockUpdate превысили 200 мс, а девять 404 относились к намеренно скрытому предыдущим тестом товару. [Повтор до настройки кэша](stage4_pre_tuning_load_results.json) получил 49 ответов 503 карточек на прогреве; [HTTP-метрики](stage4_warmup_diagnostics.json) подтверждают 29 и 20 ответов на двух API, отдельно от readiness. Его основной профиль пересёкся с Docker/Maven build на том же хосте, провалил пороги и не используется как подтверждение ёмкости. Финальный прогон выполнен без параллельных сборок; оба его профиля прошли.

В первом raw k6 min media составил −0,156 мс, что физически не интерпретируется как длительность. На таком масштабе локальных задержек минимум зависит от точности клиентского таймера; выводы опираются на p95/p99, ошибки и фактический объём запросов. В финальном профиле min положителен. Для удалённой сети/CDN потребуются отдельные измерения.

Регрессия ядра на финальном коде также [пройдена](stage4_core_regression.json): 1000 попыток покупки → 100 заказов и 900 отказов по остатку; 64 повтора → один заказ/резерв; конкурентное истечение, Redis fallback и multi-SKU rollback безопасны. Dump/restore восстановил 200 106 заказов и 600 109 позиций с совпавшими fingerprints, restore занял 2,96 с на этом малом стенде. Исторические планы запросов этапа 2 сохранены.

Согласованность сводки и README проверяется `python3 scripts/analyze_stage4.py --check`.

## Исправления по результатам интеграции

Garage v2.1 использует ключ `GK` + 24 hex-символа; образ запускается командой /garage server. Числовой тестовый secret обязательно заключён в кавычки YAML: иначе Compose преобразует длинное число, и SigV4 получает 403. Для Hikari применены явные DB_POOL_WAIT_MS/DB_INIT_SQL placeholders: некорректное разбиение имени параметра environment заставляло binder обращаться к DataSource.getConnection до окончания конфигурации пула. Эти ошибки обнаружены запуском реальных компонентов и исправлены в Compose/скриптах.

Один Mac не доказывает RPO/RTO при потере узла или AZ. SLO, мониторинг/алерты, операционный retention, надёжное размещение, fencing/failover и повторное восстановление входят в этап 5. В текущем стенде фиксированы лимиты памяти и параллельности, durable volumes и проверяемые границы повторной обработки. Проектные стоимости SQL из модели не являются трассировкой прототипа: два publisher опрашивают outbox раз в 200 мс, rebuild scheduler тоже выполняет SQL при отсутствии активной job. Настройка адаптивного idle polling и пересчёт фонового SQL относятся к следующей эксплуатационной доработке.

Остановка с сохранением данных:

```bash
docker compose -f infra/stage4/compose.yaml down
```

`down --volumes` удаляет данные указанного учебного проекта; для обычной остановки этот флаг не нужен.
