# Проверки этапа 1

## Расчётная модель

Команда `python3 scripts/calculate_capacity.py --check` проверяет сумму долей регионов, допустимые доли воронки/кэшей и соответствие сгенерированных таблиц текущей JSON-модели. Дополнительно сопоставлены исходные группы действий, число попыток/заказов/оплат и объекты годовой истории.

Результат: расчёт и сводка README соответствуют модели. Это арифметическая проверка; значения DAU, размеров, конверсий и hit ratio остаются допущениями.

## Функциональный стенд балансировки

Выполнена команда:

```bash
python3 scripts/check_balancing.py --start
```

Окружение: локальный Docker Engine 29.9.2, образы `haproxy:3.2-alpine` и `eclipse-temurin:25-jdk`; лимит памяти Java-контейнера 256 МиБ, heap 128 МиБ, CPU 0,5. HAProxy и три Java-процесса находятся на одном хосте. Программа создаёт выделенный Compose-проект и завершает его после проверки.

| Проверка | Наблюдение |
| --- | --- |
| Round-robin | Из 20 запросов 10 обработал commerce-1 и 10 commerce-2 |
| Маршрутизация | `/api/search` и вложенный путь попали в Search; `/api/search-other` — в Commerce; путь загрузки — в uploads backend |
| «Ложная живость» | У commerce-1 readiness стал 503 при живом PID 1; HAProxy исключил его за 5,91 с в этом прогоне |
| Работа оставшегося экземпляра | 10 последующих запросов обработал commerce-2 |
| Изоляция поиска | Search продолжил отвечать при исключённом Commerce-экземпляре |
| Graceful shutdown | Два начатых медленных запроса, по одному на экземпляр, завершились успешно при остановке commerce-1 |
| Восстановление | После возврата readiness и после повторного запуска экземпляр вернулся в пул |
| Завершение стенда | Compose-проект остановлен и удалён |

Запуск HAProxy также подтвердил, что конфигурация принимается реальным процессом. Повторный прогон может дать другое время обнаружения из-за фазы health checks и локального планировщика; 5,91 с — одно наблюдение, а не SLO.

## Границы результата

Проверены HTTP-routing, round-robin, active readiness, исключение/возврат экземпляра и завершение начатых запросов. Эти Java-процессы — диагностические заглушки, которые не обращаются к PostgreSQL или провайдеру оплаты.

Публичный TLS, реальный CDN, несколько AZ, отказ L4-точки входа, корректность заказов/платежей и производительность бизнес-API этим прогоном не проверяются. Нагрузочные измерения JVM/SQL и F01/F02 выполняются после реализации соответствующей логики.
